# 가입 정책 확인·소셜 연결 해제 FE 합의안

2026-10-18. **합의 전 제안이며 API 필드·DB·가입 동작을 변경하지 않았습니다.** BE-01~04와 별도 배포합니다.

## BE-05 합의가 필요한 계약

| 의미 | 제안 | 미합의 사항 |
| --- | --- | --- |
| 연령 확인 | 생년월일·신분증 대신 만 14세 이상 자기 확인 boolean. 누락/false는 통과시키지 않음 | 최종 필드명·확인 UI·실제 나이 검증 필요 여부 |
| 개인정보 안내 확인 | 서버가 허용하는 정책 version과 확인 시점(서버 시각) 기록 | 최초 정책 version·재확인 대상 변경 기준 |
| 실제 동의 | 필수/선택/공유/국외 이전의 필요한 항목을 각각 구분. 한 boolean으로 모두 동의 처리하지 않음 | 운영 책임자가 필요한 항목·근거·거부 결과를 확정 |
| 접수 API | 최초 가입 또는 가입 프로필 완료에서 검증. 서버가 정책 version과 boolean의 정확한 형식을 확인 | OAuth에서 계정을 먼저 생성할지, 확인 전 임시 상태 수명/정리 방식 |
| 응답 | 확인이 필요한 상태와 미충족 항목/정책 version을 FE가 구분 가능하게 반환 | 최종 DTO·오류 코드·HTTP status |
| 재시도 | 같은 사용자·version·동의 항목 반복 확인은 멱등. 클라이언트 확인 시각을 증거 시각으로 신뢰하지 않음 | 변경·철회 이력 보존 기간 |

후보 필드명을 즉시 고정하지 않습니다. 합의 후 별도 ADR과 OpenAPI 초안을 작성하고 FE 계약 테스트를 먼저 추가합니다. 자기 확인은 본인확인 기관을 통한 실제 나이 검증과 다른 수준입니다.

## 호환 배포 제안

1. 상태 조회 기능을 additive로 준비하고 신규 필드를 FE가 읽을 수 있도록 업데이트합니다.
2. 기존 사용자의 확인 이력을 임의 true로 백필하지 않습니다. 미확인 상태로 두고 재확인 UX/기한·제한 범위를 합의합니다.
3. 신규 가입·재가입(새 UUID)은 새 확인이 필요합니다. 프로필 작성 중 재개 시 서버 확인 상태와 정책 version을 다시 조회합니다.
4. 구버전 클라이언트는 필드를 보내지 않으므로 강제 활성화 시 실패하게 됩니다. 최소 지원 버전 안내·업데이트 경로를 준비한 뒤 활성화합니다. 누락을 자동 동의로 간주하는 fallback은 두지 않습니다.
5. 합의 후 migration(확인 이력·unique/idempotency·기간) → 호환 서버 → FE → 강제 적용 순서로 배포합니다. 필수 기능 거부/선택 거부/철회 영향은 각각 테스트합니다.

필수 QA: 미전달/false/잘못된 version/문자열 true/동시 반복/구버전/기존 사용자/재가입/프로필 재개/정책 변경/선택 거부/공유 차단/철회. 실제 앱 통합 검증 전에는 완료로 표시하지 않습니다.

## Google/Naver 경계 확인 결과

인접 Flutter 저장소의 다음 코드를 직접 확인했습니다.

- `lib/features/auth/data/repositories/auth_repository_impl.dart`의 `deleteAccount()`는 Google 연결 사용자이면 Google disconnect 후 Naver disconnect를 호출하고 서버 DELETE를 요청합니다.
- Google 서비스는 SDK disconnect를 await하며, 초기화/설정/SDK 오류가 발생하면 서버 접수까지 도달하지 않을 수 있습니다.
- Naver 서비스는 현재 SDK access token이 없으면 바로 반환하고, 토큰이 있으면 `logOutAndDeleteToken()`을 실행합니다. 토큰 부재를 provider 서버 연결 해제 완료로 해석할 수 없습니다.
- 서버는 Apple/Kakao 해제만 담당하며 이번 작업에서 Google/Naver 서버 revoke를 추가하지 않았습니다.

| 시나리오 | 현재 경계/합의 필요 처리 |
| --- | --- |
| SDK 세션 없음·만료 | Google SDK 결과 및 Naver 토큰 부재/만료 분기를 실기기로 확인. 서버 삭제 접수를 영구 차단하지 않는 재인증/지원 경로 합의 |
| SDK 해제 성공 후 서버 5xx/네트워크 실패 | 앱 JWT가 유효한 동안 서버 접수 재시도. 외부 해제 재시도 실패만으로 내부 삭제가 막히지 않게 상태 설계 필요 |
| 서버 접수 성공 후 응답 유실 | 서버의 진행 중 응답과 상태 조회로 수렴. 동일 요청이 전체 해제를 증명하지 않음 |
| 앱 접근 불가 지원 요청 | 이메일 본인확인·승인·접수 감사 절차는 운영자가 확정. 현재 새 CLI는 **기접수 작업 재시도만** 지원하며 수동 신규 탈퇴 접수를 제공하지 않음 |

다음 담당자: FE 담당자는 SDK 경계·정책 UI/DTO 제안, 운영자는 실제 동의 항목·구버전/기존 사용자 처리·수동 신규 접수 정책, BE는 합의 후 migration/OpenAPI/강제 검증 구현.
